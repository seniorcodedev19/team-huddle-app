# v1.2 - Review: Pub/Sub, Redis and the Reference Architecture

**Status:** review for decision. No code changed.
**Audience:** the owner, deciding what to build for real-time notifications.
**Companion:** [v1.2-architecture.md](v1.2-architecture.md), [v1.2-design.md](v1.2-design.md)

---

## 1. The short answer

The diagram is a correct, conventional design for a real-time system at scale.
It is also roughly **two orders of magnitude larger than this application**, and
adopting it now would add four moving parts that solve problems this system does
not have.

My recommendation: **build the seam the diagram implies, not the infrastructure.**
One interface, an in-process implementation today, Redis behind it the day a
second backend instance exists.

---

## 2. What the numbers say

Measured against the live database, not estimated:

| Signal | Value |
|---|---|
| Users | 13 total, **9 active** |
| Audit events, last 7 days | **370** (~2 per hour) |
| Board cards | 92 |
| Interviews | 4 |
| API runtime dependencies | **5** (`cors`, `express`, `jose`, `pg`, `zod`) |
| Deploy config in repo | none committed |

Nine people generate about two notifiable events an hour. A single Node process
handles that with the event loop idle essentially all of the time.

The diagram's components - Envoy, two load-balanced worker pods, Redis
Enterprise, Supabase Realtime - are each justified somewhere between thousands
and millions of concurrent connections. The gap is not marginal.

---

## 3. Component by component

### API Gateway / Envoy - **not yet**

Buys TLS termination and rate limiting. Both are real needs, and both are already
solved more cheaply: a managed host (Render, Fly, Vercel) terminates TLS for you,
and rate limiting belongs at that edge too.

Worth noting independently of this diagram: **there is no rate limiting anywhere
in the app today**, including on `/auth/login`, and no lockout. That is a genuine
gap, and it is a reason to put a managed edge in front of the API - not a reason
to run Envoy.

### Two load-balanced worker pods - **this is the real decision**

Everything downstream of this box exists *because* of it. One process needs no
shared event bus; two do, because a notification published on pod A must reach a
browser holding an SSE stream on pod B.

So the question is not "Redis or not". It is **"one backend process or more than
one?"** At 9 users the answer is one, and a single process on a host with
automatic restarts is more available in practice than two pods with a hand-rolled
bus between them.

### Redis Enterprise pub/sub - **right mechanism, wrong tier, wrong time**

Redis pub/sub is the correct way to fan out across processes. Two caveats the
diagram does not show:

- **Redis pub/sub is fire-and-forget.** A subscriber that is down when a message
  is published never receives it. For notifications that must survive a reconnect,
  the durable record has to live in Postgres anyway - which is exactly what
  `activity_recipients` already does in the v1.2 design. Redis would carry the
  *liveness*, not the truth.
- **Enterprise** is a licensed tier for clustering, HA and support. Nothing here
  needs it. A single managed Redis instance would do, when the time comes.

### Supabase Realtime (WAL listener) - **overlaps, and changes the trust model**

This is the component I would push back on hardest.

Listening to the Postgres write-ahead log means notifications are triggered by
*rows changing*, not by the application deciding something is worth telling
someone. That sounds like a feature. In practice it means:

- Notification logic moves out of the code that knows the intent. `audit()`
  knows *why* a row changed and who should hear about it; a WAL listener sees
  only that a row changed.
- Every write becomes a potential notification, including migrations and
  backfills. Migration 025 touched all 92 cards - under WAL-triggered
  notifications that is 92 events to suppress.
- It duplicates the Redis path immediately beneath it. The diagram has two
  independent event sources feeding the same bus, with no stated rule for which
  wins.

If the app ever needs to react to changes made *outside* the API - direct SQL, a
second service - WAL listening earns its place. Today every write goes through
one Express app.

## 4. What I would build instead

The v1.2 design already has the right shape. Stated as a seam:

```
  route handler --> audit(..., notify) --> INSERT audit_log          (the truth)
                                       --> INSERT activity_recipients (who, read state)
                                       --> bus.publish(userIds, ev)   (liveness only)
                                                   |
                                                   v
                                        +----------------------+
                                        |  NotificationBus     |   <- one interface
                                        +----------------------+
                                          |                  |
                                 InProcessBus          RedisBus
                                 (today)               (when pods > 1)
```

```ts
interface NotificationBus {
  publish(userIds: number[], event: ActivityEvent): Promise<void>;
  subscribe(userId: number, send: (e: ActivityEvent) => void): () => void;
}
```

`InProcessBus` is an `EventEmitter` - perhaps 30 lines. `RedisBus` publishes to a
channel and subscribes on connect. **Swapping them is a one-line change at
startup**, because nothing above the interface knows which is in use.

This is the whole value of the diagram, kept, at none of its cost.

### Why Postgres stays the source of truth

Whichever bus is in use, a client that reconnects asks for everything newer than
its last seen id, and that query hits `activity_recipients`. The bus only makes
delivery *immediate*; it is never what makes delivery *reliable*. Keeping that
boundary is what allows the transport to change without risking lost
notifications.

## 5. When each piece earns its place

| Trigger | Add |
|---|---|
| A second backend instance, for any reason | `RedisBus` |
| Sustained concurrent SSE streams in the hundreds | Managed edge with connection limits |
| Writes arriving from outside the API | WAL listening, or `LISTEN/NOTIFY` first |
| Notifications must survive a backend restart in flight | Durable queue - but check `activity_recipients` does not already cover it |
| Any public endpoint under abuse | Rate limiting at the edge - **worth doing before the others** |

Note the fourth row. Several problems the diagram solves with infrastructure are
already solved in the v1.2 schema. That is worth checking before adding a
component.

### A middle step the diagram skips

Postgres has `LISTEN`/`NOTIFY` built in. It gives cross-process fan-out with **no
new infrastructure** - the database is already there and already connected. Its
limits are real (8KB payloads, no delivery guarantee, a connection held open per
listener), but for a second or third pod it is often enough, and it fits behind
the same `NotificationBus` interface.

If the goal is "survive adding one more instance", this is a smaller step than
Redis and worth trying first.

---

## 6. Risks if the diagram is adopted now

| Risk | Why it matters here |
|---|---|
| Operational surface | 5 dependencies becomes 5 + Redis + Envoy + Supabase Realtime. Each can fail, and each needs someone who knows it |
| Two event sources, no arbitration | Redis and WAL both feed the bus with no stated precedence; duplicate notifications are the likely first symptom |
| Fire-and-forget assumed durable | Redis pub/sub drops messages to absent subscribers. Without the Postgres record, reconnects lose notifications silently |
| Cost | Redis Enterprise plus a managed gateway, to serve nine people |
| Harder to debug | A missing notification now has five places to hide instead of one |
| Delays the feature | None of this makes the notification *work*; it makes it scale. The feature is what the team actually needs |

---

## 7. Recommendation

1. **Build phases 1-3 as designed.** Polling, durable `activity_recipients`,
   Postgres as truth. The feature becomes usable.
2. **Introduce `NotificationBus` in phase 4**, with the in-process
   implementation. The seam exists; the infrastructure does not.
3. **Add `RedisBus` when a second instance appears** - not before. It is a
   one-line startup change by then.
4. **Consider `LISTEN`/`NOTIFY` before Redis** if that moment comes while the
   scale is still modest.
5. **Add rate limiting at the managed edge soon**, independent of all of this.
   It is the one genuine gap the diagram points at.

The diagram is a good picture of where this could go. The seam is what makes
getting there cheap; the components are what make getting there expensive today.
Build the seam now and the rest stays a configuration change rather than a
rewrite.
