# v1.2 - Design: Board Cards & Notifications

**Status:** proposal for approval. No code has been changed.
**Audience:** the owner, reviewing before implementation starts.
**Companion:** [v1.2-architecture.md](v1.2-architecture.md) - schema, API, delivery.

Every screen below reuses the existing class vocabulary (`card`, `panel`,
`chip`, `btn`, `dd`, `banner error`, `empty`) and the existing CSS tokens
(`--ink`, `--muted`, `--surface`, `--line`, `--accent`, `--s0`-`--s5`). No
Tailwind, no CSS-in-JS, no new colour values.

---

## 1. Board card

Cards stay on the kanban as they are today, with one addition: the card key.
Nothing else about the board changes in this version - drag-to-move still works
exactly as it does now.

```
+------------------------------------------+
| [icon]  Upwork                  TRN-184   |
|         Mark Chen - AI                    |
|                                           |
|  (D)  Daniel Ong              [3 comments]|
+------------------------------------------+
```

- The key sits top-right, quiet - `--muted`, tabular numerals so keys align
  down a column.
- The comment count appears **only when there is at least one**, so a quiet
  card stays quiet.
- Clicking anywhere on the card opens the modal. Dragging still moves it; the
  click handler fires only when no drag occurred.

## 2. Card modal

Opens over the board. Same component as the detail page - one implementation,
two mounts.

```
+----------------------------------------------------------------+
| [icon] Upwork - Mark Chen - AI                 TRN-184     [x]  |
+--------------------------------------+-------------------------+
|                                      | Assignee                |
|  Site notes                          |  [ (D) Daniel Ong    v ] |
|  Freelance marketplace; profile      |                         |
|  approval takes 2-3 days.            | Status                  |
|                                      |  [ * Approved        v ] |
|  Account                             |                         |
|  mark.chen@example.com               | Created                 |
|                                      |  2 Nov 2026             |
|  ----------------------------------  |                         |
|  Comments                        (3) | Updated                 |
|                                      |  8 Nov 2026 by Jack     |
|  (J) Jack  - 2h ago                  |                         |
|      Approved, ready for @Daniel Ong | Site                    |
|                                      |  upwork.com  [open]     |
|  (D) Daniel Ong  - 1h ago            |                         |
|      Thanks, starting today.         |                         |
|                                      |                         |
|  +--------------------------------+  |                         |
|  | Write a comment... use @ to    |  |                         |
|  | mention someone                |  |                         |
|  +--------------------------------+  |                         |
|                        [ Comment ]   |                         |
+--------------------------------------+-------------------------+
```

**Layout.** Content left, metadata rail right - the arrangement in your Jira
reference. The rail is a fixed 240px; the content column takes the rest.

**Header.** Site icon (`training_sites.icon_url`, falling back to the existing
`SiteLogo` component), then `Site - Profile`, then the key.

**Status and Assignee** are live dropdowns, not labels. Changing either saves
immediately and writes an activity - no separate Save button, matching how the
rest of the app already behaves.

**Responsive.** Below 860px the rail stacks *above* the comments rather than
below, so status stays reachable without scrolling past the thread. This
matches how the calendar sidebar already collapses.

## 3. Detail page

`/ai-training/board/[cardNo]` renders the same panel full-width with a back
link to the board. This exists so a notification can link somewhere - a modal
alone has no URL.

```
AI Training  >  Board  >  TRN-184
```

Server component fetches with `tryFetch`, rendering `<div className="banner
error">` on failure, like every other page. An unknown key renders the standard
not-found rather than an error.

## 4. The @ mention picker

Typing `@` in the comment box opens a filtered list below the caret.

```
  Write a comment...
  Approved, ready for @dan|
                     +--------------------------+
                     | (D) Daniel Ong           |
                     |     daniel@example.com   |
                     +--------------------------+
                     | (D) Dani Cruz            |
                     |     dani@example.com     |
                     +--------------------------+
```

- Filters on name and email as you type.
- Up/Down move, Enter or Tab select, Escape closes without selecting.
- Selecting inserts the display name and records the **user id** in `mentions`.
  Storing the id, not the text, means a later rename cannot change who was
  notified.
- Reuses the existing `Dropdown` component. No combobox library.

Mentioned names render as a subtle `--accent` chip in posted comments.

## 5. Notification bell and panel

Placed in the sidebar, following your Atlassian reference.

```
+---------------------------+
| Notifications        [x]  |
|                           |
| Direct | Watching         |
| ------                    |
|                     [o ]  |
|          Only show unread |
|                           |
|  * Jack commented on      |
|    TRN-184                |
|    "Approved, ready for   |
|     @Daniel Ong"          |
|    2h ago                 |
|                           |
|    Sarah rescheduled      |
|    Interview: Acme        |
|    10:00 AM -> 11:00 AM   |
|    4h ago                 |
|                           |
|  [ Mark all as read ]     |
+---------------------------+
```

**Bell.** Sits in the sidebar nav. Unread count as a badge; no badge at zero.
The count is capped at `9+` so the sidebar never reflows.

**Tabs.** *Direct* is anything naming you - assigned, mentioned, added.
*Watching* is activity on things you follow. If watchers are deferred
(architecture doc, decision 3), the Watching tab is hidden rather than shown
empty - an empty tab that can never fill reads as broken.

**Only show unread** is a toggle, matching the reference. The choice persists
in `localStorage`, wrapped in try/catch like the existing theme script.

**Empty state** uses the existing `.empty` class: "You have no notifications
from the last 30 days."

**Read behaviour.** Opening the panel does *not* mark everything read -
that would defeat the purpose of coming back to it. An item marks read when
clicked, or via "Mark all as read".

**Clicking** a notification navigates to the thing it is about: a card key goes
to the detail page, a calendar event to that week.

## 6. Desktop notifications

Off until asked for. A toggle in the panel footer reads "Also notify me on this
device". Tapping it is the deliberate action that triggers
`Notification.requestPermission()`.

Three states, all handled:

| State | What the toggle shows |
|---|---|
| Not yet asked | "Also notify me on this device" - off |
| Granted | On |
| Denied | Disabled, with "Blocked in your browser settings" |

A denied permission is not an error and never produces a banner. The in-app
bell keeps working regardless.

Desktop toasts fire only when the tab is hidden - a toast for something already
visible on screen is noise.

## 7. Activity phrasing

Built at read time from `action`, `entity` and `detail`. Each line names who,
what, and which thing - never a bare "record updated".

| Activity | Reads as |
|---|---|
| Comment | Jack commented on TRN-184 |
| Status | Jack moved TRN-184 from Created to Approved |
| Assignee | Admin assigned you TRN-184 |
| Profile | Admin added you to Mark Chen - AI |
| Event created | David created Interview: Acme stage 2 |
| Event moved | Daniel rescheduled Interview: Acme, 10:00 AM to 11:00 AM |
| Event cancelled | Sarah cancelled Interview: Acme stage 2 |

Second person throughout ("assigned **you**") when you are the recipient - it
is a notification, not a log line.

Timestamps are relative under a day ("2h ago"), absolute beyond it
("2 Nov"), with the full value in a `title` attribute.

## 8. What this design deliberately does not do

Listed so the scope is unambiguous before approval:

- **No comment editing or deleting.** The column is reserved; the UI is not
  built.
- **No rich text or attachments.** Plain text with `@` mentions only.
- **No reactions, no threading.** A flat chronological list.
- **No changes to drag-and-drop.** The board behaves as it does today.
- **No email digest.** In-app and desktop only.
- **No per-user notification preferences** beyond the desktop toggle. Which
  events notify whom is fixed by the table in the architecture doc.

Each is additive later; none is blocked by what is above.
