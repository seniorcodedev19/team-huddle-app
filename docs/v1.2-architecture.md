## 2. Data model

### 2.1 Card identity

Board cards are `training_accounts` rows - a `(profile_id, site_id)` pair with
no human-facing ID.

```sql
-- 025_card_keys.sql
alter table training_accounts add column if not exists card_no int;

-- Backfill in a stable order so keys never shuffle on re-run.
with ordered as (
  select id, row_number() over (order by id) as n from training_accounts
)
update training_accounts t set card_no = ordered.n
from ordered where ordered.id = t.id and t.card_no is null;

create sequence if not exists training_card_no_seq;
select setval('training_card_no_seq',
              coalesce((select max(card_no) from training_accounts), 0) + 1,
              false);

alter table training_accounts
  alter column card_no set default nextval('training_card_no_seq'),
  alter column card_no set not null;

create unique index if not exists training_accounts_card_no_idx
  on training_accounts (card_no);
```

Displayed as **`TRN-184`**. Assigned at creation, never reused, so a shared
link stays meaningful even after deletion.

> **The existing upsert keeps working.** `/training-accounts` upserts on
> `(profile_id, site_id)`. `card_no` defaults on insert and is untouched on
> conflict, so editing a card keeps its key.

### 2.2 Comments

```sql
-- 026_card_comments.sql
create table if not exists card_comments (
  id          bigserial primary key,
  account_id  int not null references training_accounts(id) on delete cascade,
  author_id   int not null references users(id) on delete cascade,
  body        text not null,
  -- Who was @-mentioned, resolved at write time. Stored rather than re-parsed
  -- so a later rename cannot silently change who was notified.
  mentions    int[] not null default '{}',
  created_at  timestamptz not null default now(),
  edited_at   timestamptz
);
create index if not exists card_comments_account_idx
  on card_comments (account_id, created_at);
```

### 2.3 Activity recipients

`audit_log` stays exactly as it is - append-only, all 33 call sites untouched.

```sql
-- 027_activity_recipients.sql
create table if not exists activity_recipients (
  activity_id bigint not null references audit_log(id) on delete cascade,
  user_id     int    not null references users(id) on delete cascade,
  read_at     timestamptz,
  primary key (activity_id, user_id)
);

create index if not exists activity_recipients_unread_idx
  on activity_recipients (user_id, read_at, activity_id desc);
```

An `audit_log` row with no recipients is a plain audit entry, as today. One
**with** recipients is a notification. That is the spec's `notification` tag -
expressed as a relation, so "who should see this" and "has it been read" are
the same fact rather than two that can drift.

## 3. API surface

### 3.1 Extending `audit()`

One optional parameter, fully backward compatible:

```ts
export async function audit(
  actorId: number | null,
  action: string,
  entity: string,
  entityId: string | number | null,
  detail?: unknown,
  notify?: number[],        // NEW - recipients
): Promise<number>          // NEW - returns the activity id
```

With a non-empty `notify` it writes the recipient rows **and** publishes to the
live bus. The 33 existing calls pass no `notify`, so their behaviour is
unchanged.

Two rules live inside the helper so no call site can get them wrong:

- **The actor is never notified of their own action** - `notify` is filtered
  against `actorId`.
- Recipient ids are de-duplicated.

### 3.2 Routes

| Method | Path | Purpose |
|---|---|---|
| `GET` | `/notifications?limit=&before=` | Current user's feed, newest first |
| `GET` | `/notifications/stream` | SSE; pushes each new activity |
| `POST` | `/notifications/read` | Mark ids, or all, as read |
| `GET` | `/cards/:cardNo` | Card with site, profile, assignees, comments |
| `GET` | `/cards/:cardNo/comments` | Thread, paged |
| `POST` | `/cards/:cardNo/comments` | Add comment; notifies assignees + mentions |
| `PATCH` | `/cards/:cardNo` | Status, note, account email |
| `GET` | `/mentionables?q=` | Users for the `@` picker |

All follow existing conventions: `h()` wrapper, Zod validation, `HttpError` for
expected failures, user-facing prose in messages.

## 4. Real-time delivery

### 4.1 Why this needs care

The agent's SSE stream is short-lived - one request, one answer. A notification
stream stays open for a whole session, which collides with two existing facts:

- **The API token lasts 2 minutes** (`api.ts:33`). A stream outliving it would
  die mid-connection.
- **Serverless pooling uses `max: 1`** (`db.ts:47`). Each held-open stream pins
  the only connection.

### 4.2 Design

```
  route handler --> audit(..., notify) --> INSERT audit_log
                                       --> INSERT activity_recipients
                                       --> bus.publish(userIds, activity)
                                                   |
                           +-----------------------+   in-process EventEmitter
                           |                       |
                           v                       v
                    /notifications/stream   (one subscriber per open tab)
                           |
                           v  text/event-stream
                    NotificationProvider (client)
                           |--> bell badge + panel
                           +--> Notification API (desktop, on permission)
```

**The token problem.** The stream authenticates once at connect, then the
connection is trusted for its lifetime. The 2-minute token gates *opening* the
stream, not holding it. The client already mints a fresh token per request, so
reconnects are free.

**Reconnect and gap-filling.** SSE's native `Last-Event-ID` carries the last
activity id seen; on reconnect the server replays anything newer. This is the
single most important detail for "no refresh required" to hold on a sleeping
laptop or dropped WiFi - not just on a fast network.

**Heartbeat.** A comment line every 25s stops proxies closing an idle stream.

**Serverless caveat, stated plainly.** On Vercel/Lambda this holds a connection
per open tab against `max: 1`, and in-process fan-out does not cross instances.
SSE suits a long-running host (Render, Fly, a VM). If the app moves to
serverless later, the transport swaps to polling behind the same client hook -
section 6 keeps that a one-file change.

### 4.3 Desktop notifications

`Notification.requestPermission()` is called **only after a deliberate user
action** - a toggle in the panel, never on page load. Browsers reject and
penalise unprompted requests. Denial is a normal state: the in-app bell stays
the primary channel.

## 5. What gets tracked

| Module | Action | Notifies |
|---|---|---|
| Board | Comment added | Assignees + everyone `@`-mentioned |
| Board | Status changed | Assignees |
| Board | Assignee changed | The new assignee |
| Profiles | Assignee added | The added user |
| Calendar | Event created | Profile assignees |
| Calendar | Event rescheduled | Assignees + whoever booked it |
| Calendar | Event cancelled | Assignees + whoever booked it |
| Calendar | Event updated | Assignees |

Phrasing is built at **read** time from `action`, `entity` and `detail` - never
stored as a sentence. A stored sentence freezes a name that may later change and
cannot be re-worded without a migration.

> "Jack updated TRN-184 status from Created to Approved."

Reschedule is detected by comparing `scheduled_at` before and after, so it reads
as a reschedule rather than a generic update - one of the spec's explicit
examples.

## 6. Frontend integration

```
NotificationProvider          // opens the stream, holds the list
  |__ useNotifications()      // { items, unread, markRead, markAllRead }
        |__ NotificationBell  // badge in the sidebar
        |__ NotificationPanel // Direct / Watching tabs, "Only show unread"
```

**The transport lives only inside the provider.** Swapping SSE for polling
touches that one file and nothing else.

This deliberately adds **no data-fetching library**. It follows the existing
`useAction()` + `router.refresh()` convention, with the stream pushing
invalidations.

## 8. Build order

Each phase is independently shippable and useful on its own.

| # | Phase | Delivers | Risk |
|---|---|---|---|
| 1 | Card identity + detail page | `TRN-184`, modal, shareable URL | Low |
| 2 | Comments + `@` mentions | Thread on each card | Low |
| 3 | Recipients + feed (**polling**) | Bell, panel, read state | Low |
| 4 | SSE transport | Replaces polling inside the provider | **Medium** |
| 5 | Desktop notifications | Native toasts behind a toggle | Low |
| 6 | Calendar + profile tracking | Remaining rows of section 5 | Low |

Phase 3 polls **deliberately**. It makes the whole feature usable without
waiting on the hosting decision, and phase 4 then swaps one file. If SSE turns
out wrong for your deployment, you lose one phase, not the feature.

## 9. Decisions that need you

1. **Hosting determines whether SSE is right.** The one genuinely risky piece.
   Render/Fly/VM: proceed as designed. Vercel: stay on polling. Please confirm
   before phase 4.
2. **`TRN-` as the card prefix.** Trivial to change now, painful once links are
   shared.
3. **Should watchers exist?** Your reference shows a *Watching* tab. The schema
   supports it (a recipient need not be an assignee), but nothing currently
   subscribes a watcher. Decide whether phase 3 ships a "watch this card" action
   or leaves that tab for later.
4. **Comment editing and deletion** are out of scope here. `edited_at` is
   reserved so adding them later needs no migration.
5. **Cards are `(profile, site)` accounts, not free-standing tickets.** Comments
   attach to that pairing. Independent tickets with their own titles would be a
   different table - this design does not block that, but does not build it.
